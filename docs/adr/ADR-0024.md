# ADR-0024 — Protocol Layer Isolation (Consensus Blindness)

**Status:** Accepted
**Date:** July 2026
**Related:** ADR-0017 (Consensus↔Execution Interface — implies this rule but
never stated it as a standalone invariant), ARCHITECTURE.md (Three-Layer
Model — this ADR makes that diagram's implicit boundary explicit and
enforceable)

---

## Context

`abyss-consensus` currently depends only on `abyss-core` (for `Hash256`,
`ZERO_HASH`). It has no knowledge of transfers, wallets, tokenomics, or
social posts — and it must never gain that knowledge. A BFT consensus
engine that starts branching on "is this a Transfer or a Social Post?"
has stopped being a consensus engine; it has become an execution engine
wearing a consensus engine's clothes, and every future privacy or
execution-model change now risks destabilising block finality itself.

This property currently holds **by discipline**, not by contract. Nothing
in the repository prevents a future commit from adding
`abyss-wallet = { path = "../abyss-wallet" }` to `abyss-consensus`'s
`Cargo.toml` for a seemingly small, convenient reason. ADR-0017 implies
this boundary through the pipeline it defines, but never states it as an
independent, named rule — so there is nothing to point to, and nothing
for CI to check, when a future change threatens to cross it.

The same risk is not unique to Consensus. `ARCHITECTURE.md`'s Three-Layer
Model already groups `abyss-consensus`, `abyss-tokenomics`, `abyss-wallet`,
and `abyss-social` together as peers within a single "Protocol Layer" —
but the diagram never states whether peers may depend on each other. Left
unstated, that ambiguity will eventually be resolved by whoever adds the
first convenient cross-import, not by deliberate design.

---

## Decision

**Protocol Layer crates do not depend on one another.**

Specifically:
- `abyss-consensus`, `abyss-tokenomics`, `abyss-wallet`, and `abyss-social`
  may each depend on Foundation Layer crates (`abyss-core`, `abyss-crypto`)
  and on `abyss-crypto-adapter` / `abyss-crypto-api`.
- None of them may depend, directly or transitively, on any other
  Protocol Layer crate.
- Only the Application Layer (`abyss-node`, and later the JSON-RPC/wallet
  application code from Stage 4+) is permitted to depend on multiple
  Protocol Layer crates simultaneously and wire them together.

**Consensus Blindness is the sharpest, safety-critical instance of this
general rule**: `abyss-consensus` must never know what a transaction
*means* (Transfer vs. Social Post vs. future Contract Call) — only that a
block hash did or did not reach quorum. This is worth naming explicitly
even though it is subsumed by the general rule above, because a violation
here is uniquely dangerous: it risks consensus non-determinism or
liveness bugs that are far harder to diagnose than a similar violation
in, say, `abyss-social`.

**What this does not forbid:** Protocol Layer crates depending on shared
Foundation Layer types is expected and required (e.g. all of them may use
`abyss_core::Coin` or a future `Hash256`-based commitment type). This ADR
governs lateral dependencies between Protocol Layer siblings only.

## Implementation Status

| Aspect | Status |
|---|---|
| Rule stated as an architectural decision | ✅ This ADR |
| Currently followed in practice | ✅ Verified by inspection: `abyss-consensus`, `abyss-tokenomics`, `abyss-social` each depend only on `abyss-core` (and `abyss-social` not even that, by its own design note); no cross-Protocol-Layer imports currently exist |
| Automated CI enforcement | 🟡 **Not yet implemented.** Tracked as a Stage 2 prerequisite alongside the other CI/tooling work in this repo (`.cargo/deny.toml`, `cargo-audit`, fuzz testing already exist as precedent). A dependency-graph check (via `cargo metadata` or an equivalent workspace lint) should fail CI if any Protocol Layer crate gains a same-layer dependency. |

---

## Consequences

- Future contributors have a named rule to cite when declining a
  "just add abyss-wallet as a dependency here, it's easier" request —
  turning an implicit convention into an explicit, defensible boundary.
- `ARCHITECTURE.md`'s Three-Layer Model diagram now has a stated meaning:
  same-layer crates are peers, not a dependency chain.
- Once CI enforcement lands (Stage 2), a violation becomes a build
  failure, not a code-review judgment call — consistent with this
  project's existing pattern of moving rules from prose into automated
  checks (`cargo-deny`, `cargo-audit`).
- This ADR does not itself add new code. The enforcement mechanism is
  explicitly deferred, not guessed at, per ADR-0007 ("when uncertain,
  choose the simpler architecture" — writing an unverified CI script now
  would be guessing, not deciding).
