# ADR-0022 — Cryptographic Foundation

**Status:** Accepted
**Date:** July 2026
**Related:** ADR-0006 (Replaceable Cryptographic Algorithms)

---

## Context

ADR-0006 established that business logic must never depend directly on
specific cryptographic algorithms — everything goes through an interface
in `abyss-crypto`. That ADR fixed the *pattern*; it did not fix *which*
algorithms ABYSS actually commits to. As the project moves toward Stage 2
(Storage) and eventually the privacy layer (whitepaper Section 5), that
commitment needs to be explicit.

This ADR is broader than a list of algorithm names. It is the project's
cryptographic architecture: which primitives are chosen and why, how they
compose (domain separation, transcripts, key derivation), and the policy
for changing them later.

**A note on Status vs Implementation:** `Status: Accepted` records that
the project has decided on this cryptographic direction. It does **not**
assert that every primitive listed is implemented in code today. The
`Implementation Status` table below is the single source of truth for
what actually exists — Accepted and Implemented are different axes, and
conflating them (as an earlier draft of this ADR did) risks either
overstating progress or, just as harmful, permanently deferring
architectural commitment until everything is finished. Neither serves
an auditor or a new contributor well.

---

## Decision

### Signing

**Ed25519** for account key pairs and transaction/vote signing.
Rationale: fast verification (important for BFT — every validator
verifies every vote), small signature size, wide library support and
audit history (`ed25519-dalek`), already resolved for known RUSTSEC
advisories in this codebase (see `fix/cargo-audit-vulnerabilities`
history).

### Hashing (consensus-critical, e.g. state_root/block hashing)

**BLAKE3** for all consensus-critical hashing once implemented.
Rationale: faster than SHA-256/SHA3 at comparable security margins,
built-in keyed-hashing and domain-separation support (relevant to the
domain-separation policy below), tree-hashing mode useful for future
Merkle-proof / light-client work (ADR-0003).

### Hash-to-Curve / commitment schemes

**Not yet decided.** Required once shielded transactions (Phase 3)
begin implementation. Deferred rather than guessed at, per ADR-0007
("when uncertain, choose the simpler architecture" — guessing now adds
false certainty, not real progress).

### Domain Separation Policy

Every hash or signature MUST include a fixed, purpose-specific domain
prefix (e.g. `"abyss:tx:v1:"`, `"abyss:vote:v1:"`) before the payload.
This prevents cross-protocol signature/hash reuse attacks, where a
signature valid in one context (e.g. a vote) is replayed as valid in
another (e.g. a transaction). This is a **rule**, not yet a completed
audit of every current call site — tracked as follow-up before Stage 4
(P2P), where cross-context replay risk becomes real (currently all
execution is single-process devnet, lower risk but not zero).

### Randomness

Key generation and any future nonce/blinding-factor generation MUST use
a cryptographically secure RNG (`rand` crate's `OsRng` or equivalent) —
never a seeded/deterministic RNG outside of explicitly labelled
`dev-keys` test paths. `abyss-crypto` already has a `dev-keys` feature
gate that redacts secrets in non-dev builds (per
`feat/feature-guard-devkeys` history) — this ADR formalises that
existing pattern as permanent policy, not just a convenience feature.

### Key Derivation

**Not yet decided.** BIP-32/SLIP-0010-style hierarchical derivation vs.
a simpler direct-seed model is an open question, tracked for Stage 5
(Wallet Core) rather than decided speculatively now.

### Serialisation of cryptographic material

Public keys, signatures, and hashes are represented as fixed-length byte
arrays internally and hex-encoded at any JSON/display boundary (matching
the existing `hashing::hex()` pattern in `abyss-core`). This ADR extends
that existing convention to all cryptographic material project-wide,
not just hashes.

### Crypto Agility / Upgrade Policy

Per ADR-0006, all primitives sit behind `abyss-crypto`'s interface.
This ADR adds the explicit policy: **a primitive change is a new ADR**
that supersedes the relevant section of this one (per the
no-renumbering, supersede-don't-rewrite rule — see ARCHITECTURE.md).
A primitive is never silently swapped without a recorded decision.

### Post-quantum migration

**Not decided; explicitly out of scope for this ADR.** Recorded here
only so it is not forgotten: Ed25519 is not quantum-resistant. A future
ADR should evaluate hybrid or PQ-native signature schemes before
mainnet, but forcing that decision now — with no mature, widely-audited
Rust PQ signature library ecosystem yet — would be guessing, not
deciding.

## Implementation Status

| Primitive / Policy | Decision | Implementation |
|---|---|---|
| Ed25519 signing | Accepted | ✅ Implemented (`abyss-crypto-adapter`, sign/verify tested) |
| BLAKE3 consensus hashing | Accepted | 🟡 Not implemented — current `abyss-core::hashing` uses a **development placeholder** (`dev_hash`). **This placeholder is NOT consensus-critical-safe and MUST NOT appear in a production or mainnet build.** Replacing it with BLAKE3 is required before Stage 2 (Storage) treats any hash as durable/canonical. |
| Domain separation | Accepted (policy) | 🟡 Not audited across existing call sites |
| Secure RNG / dev-keys gating | Accepted | ✅ Implemented (`dev-keys` feature, `feat/feature-guard-devkeys`) |
| Hash-to-curve / commitments | Not decided | — (Phase 3 prerequisite) |
| Key derivation scheme | Not decided | — (Stage 5 prerequisite) |
| Hex encoding at boundaries | Accepted | ✅ Implemented for hashes (`hashing::hex`); not yet extended to all key/signature material |
| Post-quantum migration | Explicitly deferred | — |

## Consequences

- The project now has a named cryptographic direction (Ed25519 + BLAKE3)
  rather than leaving hashing as an undocumented placeholder indefinitely.
- The `dev_hash` production-safety gate is now written down as a hard
  rule, not just an implicit understanding — reducing the risk that it
  quietly ships in a real build a year from now.
- Future privacy-layer primitives (commitment schemes, ring signatures,
  or whatever Phase 3 research settles on) are explicitly named as
  **not yet decided** rather than pre-committed to a specific scheme
  (e.g. CLSAG vs Seraphis) before that research is actually done —
  consistent with PHILOSOPHY.md's commitment to not presenting
  aspiration as fact.
