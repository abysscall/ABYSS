# ADR-0017 — Consensus ↔ Execution Interface

**Status:** Accepted
**Date:** July 2026

---

## Context

Stage 1 of ADR-0016 (BFT Consensus) is complete: `abyss-consensus` can
drive a validator set through Propose → PreVote → PreCommit → Commit and
produce a deterministic PreCommit QC (quorum certificate) for a block hash.

However, `abyss-consensus` and `abyss-core`'s `Chain::apply_block()`
currently exist as two separate, only loosely connected systems. The
consensus engine knows a block hash has reached quorum; `Chain` knows how
to execute a block's transactions and compute a state root. Nothing yet
defines the **contract** between them.

This gap is dangerous specifically because a Storage layer (Stage 2) is
next on the roadmap. If storage code is written against an ad hoc,
undocumented sequence of calls, it will almost certainly need to be
rewritten once the real consensus→execution→persistence pipeline is
defined. Fixing the interface first is cheaper than fixing it twice.

---

## Decision

Define and document the following as the canonical block lifecycle. Every
future component (Storage, P2P, RPC) is built against this sequence, not
around it:

```
1. propose_block()      — [Consensus/Proposer]  build a candidate block
                           from mempool transactions
2. verify_block()        — [Consensus/Validator] structural checks:
                           height, previous_hash, signature presence
3. execute_block()       — [Execution]            apply all transactions
                           to a staged copy of State (ADR-0004: atomic)
4. calculate_state_root() — [Execution]           hash the resulting State
5. compare_state_root()   — [Consensus]           staged root must equal
                           the root claimed in the block header
6. vote(PreVote)          — [Consensus]           if 5 passes, vote
7. vote(PreCommit)        — [Consensus]           on PreVote QC
8. commit_state()         — [Execution]           on PreCommit QC,
                           staged State becomes canonical
9. persist()               — [Storage, Stage 2]    write block + state
                           to durable storage
10. finalize()              — [Consensus]           advance height,
                           reset round state
```

Steps 2–5 are **already implemented** today as `Chain::apply_block()` in
`abyss-core`, which performs exactly: height check → previous_hash check →
staged execution → state_root comparison, atomically (verified by
`apply_block_validates_height_and_previous_hash`,
`apply_block_rejects_wrong_height`, and
`state_root_is_consistent_between_proposer_and_validator` in the current
test suite).

What is **not yet implemented** is steps 6–10 as an explicit, wired
pipeline: `ConsensusEngine` currently reaches a PreCommit QC but does not
yet call into `Chain::apply_block()` to actually commit state, nor into a
persistence layer. This ADR defines the target sequence; wiring
`ConsensusEngine` to `Chain` and to Storage is tracked as explicit
follow-up work before or alongside Stage 2.

**Naming conventions established by this ADR:**
- `verify_block()` = structural/consensus-level checks only (no execution)
- `execute_block()` = transaction application (already exists as the
  internal staging step inside `apply_block()`)
- `commit_state()` = replacing canonical State with staged State
  (already exists as the `*self = staged` step inside `apply_block()`)
- `persist()` = the new responsibility Stage 2 (Storage) adds

---

## Consequences

- Storage (Stage 2) can now be designed against a known interface: it
  needs to durably persist the *output* of `commit_state()` — i.e., after
  `Chain::apply_block()` succeeds — not invent its own execution logic.
- Future replacement of the in-memory devnet transport (Stage 3, P2P)
  slots into steps 1–2 (receiving a proposed block from the network)
  without touching steps 3–10.
- This ADR does not itself change any code. It is a naming and
  sequencing contract. Follow-up work: wire `ConsensusEngine::commit()`
  to actually invoke `Chain::apply_block()` rather than only advancing
  its own internal height counter.

**Explicitly deferred by this ADR** (not yet decided):
- Where State lives physically (in-memory vs RocksDB) — Stage 2.
- Block header field list — ADR-0018.
- Full state machine shape beyond Accounts (Validators, Contracts,
  Governance) — ADR-0019.
