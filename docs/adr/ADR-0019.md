# ADR-0019 — State Machine Scope (provisional number — verify against adr/ first)

**Status:** Proposed
**Date:** July 2026

---

## Context

ADR-0005 extracted `State` from `Chain`, but scoped it deliberately to
Accounts only (`balances`, `nonces`) — matching what the devnet actually
needed at the time. ADR-0005 explicitly named future scope: Validators,
Treasury, Contracts, Governance, Storage anchors.

Stage 2 (Storage) cannot be designed correctly without knowing which of
these subsystems it must persist. Writing a RocksDB schema for "Accounts
only" and then adding Validators, Contracts, and Governance later means
either a painful migration or an ad hoc bolt-on that violates ADR-0005's
own stated goal of low coupling.

This ADR does not implement these subsystems. It fixes their *shape* so
Storage (and later, Execution) can be built against a stable target.

---

## Decision

`State` (in `abyss-core::state`) will grow to contain the following
top-level subsystems. Each is independently namespaced; none directly
reference each other's internals (per ADR-0005's low-coupling goal).

```rust
pub struct State {
    pub accounts: AccountState,       // ✅ implemented (ADR-0005)
    pub validators: ValidatorState,   // proposed here
    pub treasury: TreasuryState,      // proposed here
    pub contracts: ContractState,     // proposed here — placeholder only
    pub governance: GovernanceState,  // proposed here — placeholder only
}
```

### `AccountState` — implemented, unchanged
`balances: BTreeMap<Address, Coin>`, `nonces: BTreeMap<Address, u64>`.

### `ValidatorState` — proposed shape
```rust
pub struct ValidatorState {
    pub bonded: BTreeMap<Address, Coin>,      // staked amount per validator
    pub unbonding: BTreeMap<Address, UnbondingEntry>, // in cooldown
    pub jailed: BTreeSet<Address>,             // slashed/jailed validators
}
pub struct UnbondingEntry {
    pub amount: Coin,
    pub completion_height: u64,
}
```
This is the missing piece the consultant correctly flagged: `abyss-consensus::SlashingRegistry` currently records evidence and blocks votes at the consensus layer, but has no connection to an economic penalty. `ValidatorState.jailed` plus a `slash()` operation (bond reduction) is what closes that gap. **Not implemented by this ADR** — scope fixed, implementation is Stage 2/3 follow-up.

### `TreasuryState` — proposed shape
```rust
pub struct TreasuryState {
    pub balance: Coin,
}
```
Backing store for the "Foundation treasury" allocation already defined
in `abyss-tokenomics::TokenomicsPlan` (5,500,000 AC). Currently that
allocation exists only as a planning number; `TreasuryState` is where it
becomes a real, spendable on-chain balance once Genesis Builder (Stage 6)
runs.

### `ContractState` — placeholder only
```rust
pub struct ContractState {
    // Intentionally empty. Populated once the EVM-compatible execution
    // environment (ADR-0009) and/or the private circuit layer (Section 5
    // of the whitepaper) are implemented. Declaring the field now reserves
    // its position in State without committing to an implementation.
}
```

### `GovernanceState` — placeholder only
```rust
pub struct GovernanceState {
    // Intentionally empty. Populated once on-chain proposal/voting
    // (whitepaper Section 11, ADR-0016 Phase 3 "Governance") is designed.
}
```

---

## Consequences

- Storage (Stage 2) can persist `State` with all five subsystems present
  from day one — even though `contracts` and `governance` start empty —
  avoiding a schema migration when those subsystems gain real content.
- `ValidatorState` gives the Slashing mechanism (ADR-0016 Stage 1) a home
  for actual economic consequences, directly answering the consultant's
  critique that "Slashing Hooks" without bond/jail/penalty is an API, not
  a complete feature. This ADR does not implement that connection; it
  makes the implementation possible without further restructuring.
- `AccountState` is unaffected — no migration needed for existing tests
  (23 passing tests in `abyss-core` remain valid).

## Explicitly Not Decided by This ADR

- Contract execution model (EVM-compatible vs custom VM) — ADR-0009
  already made this decision at the whitepaper level; wiring it into
  `ContractState` is separate implementation work.
- Governance voting mechanics — deferred to Phase 3 (ADR-0016).
- Exact `slash()` penalty percentages / economics — deferred; this ADR
  only reserves the data shape (`jailed: BTreeSet<Address>`,
  `bonded`/`unbonding` maps), not the policy.
