# ADR-0020 — Transaction Specification

**Status:** Accepted
**Date:** July 2026
**Related:** ADR-0018 (Block Header Format), ADR-0021 (Execution Semantics)

---

## Context

ADR-0018 fixed the block header shape but deliberately deferred
transaction format details. `abyss-core::Transaction` already exists and
is exercised by 23 passing tests, but — as with the block header before
ADR-0018 — its field list has grown without being documented as a
deliberate, versioned contract. Per the "one ADR = one decision"
principle, transaction format is split out from block format as its own
document.

---

## Decision

### Current (implemented) fields
```
from: Address
to: Address
amount: Coin
fee: Coin
nonce: u64
memo_commitment: Hash256
```
This shape is unchanged by this ADR — it is documented as-is, matching
current `abyss-core::transaction`.

### New field reserved by this ADR
```
version: u16   — protocol version, mirrors ADR-0018's block header
                 versioning rationale. Not yet in code; tracked as
                 follow-up before Stage 2 (Storage) freezes a wire format.
```

### Signature — explicitly deferred, not yet attached to Transaction
Transactions are not yet signed in the current devnet (the CLI constructs
them directly). `abyss-crypto-adapter` already provides working
Ed25519 sign/verify (2 passing tests). Attaching a signature field and
requiring `Chain::apply_transaction()` to verify it is **follow-up work**,
sequenced before Stage 4 (P2P) — an unsigned transaction is acceptable
for a single-process devnet but not for a multi-node network where
transactions arrive from untrusted peers.

### Serialisation — three separate concerns, not one decision
The consultant's note ("not JSON inside the network") is correct but
conflates three distinct contexts that deserve separate answers:

| Context | Current | Decision |
|---|---|---|
| Devnet JSON snapshots (`storage.rs`, human-debuggable) | JSON via serde | **Keep** — this is a debug/devnet convenience, not a protocol commitment |
| Stage 2 persistent storage (RocksDB) | N/A yet | Not decided by this ADR — tracked in Stage 2 planning |
| Stage 4 P2P wire format | N/A yet | **Proposed direction: bincode**, for compactness and determinism. Not Accepted — needs its own decision once P2P framing (message headers, versioning) is scoped in Stage 4 |

This ADR does **not** commit to bincode/CBOR network-wide today. It
records the distinction so Stage 2 and Stage 4 don't silently inherit
JSON as a protocol decision by default.

### Receipts — explicitly not decided here
The consultant's proposed `receipts_root` assumes an execution model with
gas usage and event logs. Current `abyss-core` has neither. Whether
ABYSS transactions produce receipts, and what they contain, is deferred
to ADR-0021 (Execution Semantics) — inventing a `receipts_root` field
here would document a field with no defined meaning.

---

## Consequences

- Transaction format is now documented independently of block format,
  satisfying the one-decision-per-ADR principle for future changes
  (e.g. adding a `data` field for contract calls later touches this
  ADR's successor, not the block header ADR).
- Signature and receipts are explicitly named as open follow-up items
  rather than silently absent — visible in ROADMAP.md Stage 2/4 entries.
