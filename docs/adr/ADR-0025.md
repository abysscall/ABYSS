# ADR-0025 — ABYSS Identity Gateway

**Status:** Proposed — architecture finalised, implementation not started
**Created:** 2026-08-25
**Updated:** 2026-09-05 (Verify → Declare → Forget model adopted)

---

## Context

ABYSS needs a mechanism to determine which platform features a user may
access, without collecting a full identity profile. This is distinct from,
and must not be confused with, the KYC/accreditation requirements of the
token investor round (see `docs/PRESALE_STRATEGY.md` and
`constitution/SECURITY.md`). The Gateway described here governs access to
general product features (wallet, Native AI, network participation) once
those features exist. It is not a substitute for investor verification,
and it is not KYC — see Terminology below.

## Core Principle

> **ABYSS does not want to know who you are. ABYSS wants to know only
> whether you may use a specific function.**

Concretely: **Verify → Declare → Forget.**

## Terminology

This process is called **Eligibility Verification**, not KYC. KYC implies
a materially more thorough identity procedure than what is described here.
Using "KYC" to describe a phone-number-based signal would overstate what
the system actually does.

## Three Distinct Concerns — kept separate

1. **Identification** — who/where the user claims to be (Gateway input)
2. **Eligibility** — which ABYSS functions that claim unlocks (Eligibility Engine)
3. **Truthfulness declaration** — the user's own legal confirmation that
   the claim is accurate (ETD-001, a separate document — see
   `docs/legal/ETD-001.md`)

These are not merged into one artefact. The declaration is a legal layer
on top of the technical check, not a technical proof of it.

## Restriction Policy — framing

Restrictions are **not** hardcoded as "EU citizens are prohibited."
Whether a given jurisdiction is restricted depends on what the specific
ABYSS function does, what AC is in that specific context, and what
activity is being carried out — this can differ by feature and may
change as legal review progresses. The declaration and policy engine
must reference:

> "Persons whose participation is prohibited by applicable law or by
> the rules of the specific ABYSS function."

The exact jurisdiction/category list per function is defined by counsel,
not hardcoded into this ADR.

## What Is Retained

Given Verify → Declare → Forget, the default is that identifying inputs
(e.g. the raw phone number) are **not retained** once the eligibility
check completes, unless a specific legal basis requires otherwise for a
specific function (to be confirmed with counsel — see Open Questions).

What the system does retain, to make repeat access and dispute resolution
possible without keeping identity data:

```
ABYSS_ID              → internal pseudonymous identifier (not derived
                          from phone number or other identifying input)
ELIGIBILITY_RESULT     → ALLOWED / DENIED
DECLARATION_DOCUMENT   → e.g. "ETD-001"
DECLARATION_VERSION    → e.g. "1.0"
ACCEPTED_AT            → timestamp
```

This is an event record, not an identity record. Whether this record
itself constitutes personal data under GDPR (e.g. if combinable with
session/IP logs) must still be assessed by counsel — see
`docs/legal/ETD-001.md`, Data Protection Note.

## Terms Note — liability framing

The Gateway and declaration do not state that ABYSS bears no
responsibility if a restricted person gains access. The correct framing:

> ABYSS takes reasonable technical measures to restrict access by
> persons not entitled to participate in a given function. The user is
> required to provide truthful information and not to take action aimed
> at circumventing established restrictions. The user is responsible
> for intentionally providing false information or intentionally
> circumventing restrictions, to the extent such responsibility is
> permitted under applicable law.

This does not attempt to exclude any ABYSS obligation that cannot
lawfully be excluded (see `docs/legal/ETD-001.md` §9).

## Limitations — read before implementing

**Phone number country code is not proof of jurisdiction.**
It reflects where a phone number was issued, not where the holder
resides, is a citizen, or is a tax resident. It is trivially obtained
for any country through virtual number services. Internal and external
language must state this precisely:

> "A phone number is used as one technical signal for preliminary
> determination of feature availability. The phone number itself is not
> proof of the user's citizenship, residence, or tax residency."

It must never be represented, internally or externally, as a verified
compliance control by itself — it works together with the user's own
declaration (ETD-001), which is what carries the legal weight.

**Third-party processors are not covered by "Forget."**
If phone verification uses a third-party SMS provider, that provider
will retain its own logs regardless of what ABYSS itself stores. "ABYSS
does not retain the number" is not the same as "no record of the number
exists anywhere." A Data Processing Agreement with any such provider,
and disclosure of this fact, is required before this goes live.

**Plain hashing of a phone number is not anonymisation.**
Phone numbers have low entropy; a plain hash is reversible via a
precomputed lookup table. If any phone-derived value must be retained
for a specific legal reason, it requires a keyed HMAC with a
server-held secret, not a bare hash.

**This Gateway does not satisfy investor-round KYC requirements.**
The token investor round (minimum $500,000) requires materially stronger
verification than jurisdiction self-declaration. Do not reuse this
mechanism as the compliance basis for investment-related solicitation.

## Open Questions — for counsel, not decided here

1. **Sanctions/prohibited-persons screening vs. Forget.** General
   jurisdiction eligibility may reasonably rely on self-declaration plus
   a technical signal. Sanctions-list screening (OFAC, EU) is a
   different regulatory category in many regimes, where retaining
   evidence that screening occurred — not just a self-declaration — may
   be required. This ADR does not assume an answer either way; it must
   be resolved before the sanctions checkbox (ETD-001 §6) is treated as
   sufficient on its own.
2. Which specific ABYSS functions require which specific
   jurisdiction/category restrictions (per "Restriction Policy — framing"
   above).
3. Whether the minimal event record described under "What Is Retained"
   constitutes personal data under GDPR in this architecture.

## Status

Architecture agreed. Not implemented — no backend exists yet (SMS
provider integration, database, secret management for any required
HMAC keys). This ADR fixes the target design for Phase 2 (ABYSS Account)
per `constitution/ROADMAP.md`. A front-end preview exists at
`gateway.html` for review purposes only; it simulates the flow and is
not connected to any real verification backend.
