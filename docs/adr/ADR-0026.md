# ADR-0026 — Governance, Root Identity, and Scoped Capabilities

**Status:** Accepted
**Date:** 2026-09-18
**Amends:** ADR-0014 (identity model only)
**Related:** ADR-0011, ADR-0024, ADR-0025, RFC-0001, RFC-0002

---

## Context

ABYSS needs a bootstrap governance model without permanently centralising the
protocol. It also needs a single identity and authority model that Wallet,
ABYSS OS, Social, Chain Factory, and future chains can share without equating
a payment address with a human, organization, or social identity.

ADR-0014 selected a wallet-address social identity for its initial data model.
That choice conflicts with ABYSS OS's Root ABYSS ID and unlinkable-persona
model, and would make payment activity an unnecessary social identifier. The
existing social implementation is a devnet skeleton, so this is the correct
point to refine its production contract.

## Decision

### Bootstrap governance

Bootstrap governance uses an **N-of-M Genesis Council**, not a single
permanent operator. N and M are explicit genesis parameters. This ADR fixes
neither their values nor a validator count, governance threshold, stake,
recovery delay, or other numeric configuration.

The council may authorize scoped bootstrap configuration, validator setup,
upgrades, and emergency procedures. It has no implicit permanent authority.
Protocol Governance, Chain Governance, Application Governance, and temporary
Genesis Governance are separate scopes.

### Identity and credentials

The canonical hierarchy is:

```text
Root ABYSS ID → PersonaID → purpose-specific keys → addresses / receiver IDs
```

Root ABYSS IDs are self-generated. A Root ABYSS ID, PersonaID, wallet account,
payment address, and cryptographic key are different entities.

External issuers may provide a scoped credential to a PersonaID. A credential
can prove a claim such as membership, authorization, eligibility, or an
age-related property; it is neither a Root ABYSS ID nor a replacement for one.

Social production identity is a PersonaID authenticated by a purpose-specific
key. A payment address is not a social account identifier. This amends only
ADR-0014's identity decision; its commitments to decentralized storage,
selective visibility, and separated social agent authority remain in force.

### Capabilities and roles

All authority uses a capability with a namespace, subject, resource, action,
conditions, expiration, and revocation reference. Initial namespaces are:

```text
identity, finance, social, storage, commerce, organization,
infrastructure, governance, system
```

A capability cannot cross its namespace implicitly. `system` is reserved for
tightly scoped protocol, validator, genesis, upgrade, and declared emergency
operations; it is never automatically granted to users, applications, or AI
agents.

A role is only a named grouping of individually evaluated capabilities. It
cannot bypass their scope, conditions, expiry, or revocation.

### Progressive decentralisation

ABYSS is decentralized by architecture and progressively decentralized in
deployment:

```text
Bootstrap → Distributed → Decentralized → Federated
```

No bootstrap-only secret, privileged RPC method, hard-coded operator address,
or Chain Factory authority may be necessary for a later stage. All governance
and validator-set changes must be authorized, auditable state transitions.

Chain Factory remains an off-chain control plane. It may compile Blueprints,
run simulations, and prepare deployment manifests, but cannot validate
transactions, custody private keys, bypass capabilities/governance, or mutate
production state by itself. AI can propose; humans or authorized governance
approve.

## Parameter governance

Open numerical and policy parameters are recorded in
`docs/architecture/ABYSS_ARCHITECTURE_PARAMETER_REGISTER.md`. A value must be
selected only at its documented decision trigger and recorded in the
appropriate ADR, genesis configuration, or other versioned artifact. No code
or documentation may silently convert a development default into a production
parameter.

## Consequences

- `abyss-social`'s string author and view registry remain devnet-only data
  model elements until PersonaID and signed content manifests are implemented.
- Wallet, OS, Social, and future policy components share capability semantics
  but remain separated by namespace and crate boundary.
- ADR-0025's proposed Eligibility Gateway is an eligibility/credential service,
  not a Root ABYSS ID issuer.
- Existing AC v0 supply and sale code is unaffected; AC Economy remains a
  separate decision stream.
- The decision creates no production readiness or privacy claim by itself.

## Implementation status

Architecture only. No Root ABYSS ID, PersonaID, credential, N-of-M governance,
or generalized capability implementation exists in the current devnet.
