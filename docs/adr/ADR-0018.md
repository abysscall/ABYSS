# ADR-0018 — Block Header Format

**Status:** Accepted
**Date:** July 2026

---

## Context

`abyss-core::Block` and `BlockHeader` already exist and are used by both
`Chain::produce_block()` / `apply_block()` and `abyss-consensus`'s block
hash references. However, the field list has grown organically and is not
yet documented as a deliberate, stable contract. Before Storage (Stage 2)
serialises this structure to disk in a format that must remain readable
across future versions, the shape needs to be fixed and justified field
by field.

Changing the block header after data exists on disk requires either a
migration or a hard fork. Fixing it now, before persistence exists, costs
nothing; fixing it after costs a migration.

---

## Decision

The canonical `BlockHeader` contains exactly these fields, in this order:

| Field | Type | Purpose |
|---|---|---|
| `version` | `u16` | Protocol version this block was produced under. Enables future header format changes without breaking historical block parsing. **New field — not yet in code.** |
| `height` | `u64` | Sequential block number. Already implemented. |
| `previous_hash` | `Hash256` | Hash of the prior block header. Already implemented — chain linkage. |
| `state_root` | `Hash256` | Root hash of `State` after this block's transactions are applied (ADR-0005, ADR-0017). Already implemented. |
| `transactions_root` | `Hash256` | Commitment to the block's transaction list, independent of `state_root`. Already implemented. Required for future light-client / Merkle-proof support (ADR-0003). |
| `validator_root` | `Hash256` | Commitment to the active `ValidatorSet` at this height (stake distribution). **New field — not yet in code.** Required so a light client or new node can verify who was entitled to sign this block without replaying the entire chain. |
| `timestamp_ms` | `u64` | Proposer's wall-clock time at proposal. Already implemented. |
| `proposer` | `String` (→ `ValidatorId` in future) | Identity of the block proposer. Already implemented as `String`; should migrate to `abyss_consensus::ValidatorId` once `abyss-core` may depend on `abyss-consensus` types, or the reverse — see Open Question below. |
| `consensus_proof` | `QuorumCertificate` (serialised) | The PreCommit QC from `abyss-consensus` that finalised this block. **New field — not yet in code.** This is what makes a block verifiable as *finalised*, not merely *proposed*. |

`Block` itself remains: `{ header: BlockHeader, transactions: Vec<Transaction> }` — no change to this top-level split (ADR-0003 already settled this).

## Fields Explicitly Excluded (for now)

- **Signature of the header by the proposer** — deferred until
  `abyss-crypto-adapter` (already implemented, Ed25519 sign/verify) is
  wired into block production. Tracked as follow-up, not blocking Storage.
- **Gas/fee-limit fields** — deferred until the Execution Engine
  (ADR-0019 / State Machine) defines fee semantics beyond the flat
  per-transaction fee that exists today.

## Open Question (not blocking, tracked for Stage 2/3)

`abyss-core` currently has no dependency on `abyss-consensus`
(`Cargo.toml` confirms this). Adding `consensus_proof: QuorumCertificate`
to `BlockHeader` would create that dependency, or require moving
`QuorumCertificate` into `abyss-core` (or a shared crate) so both sides
can reference it without a circular dependency.
**Recommendation:** introduce a small shared crate (e.g. `abyss-proto`)
holding types referenced by both `abyss-core` and `abyss-consensus` —
`Hash256`, `ValidatorId`, `QuorumCertificate`. This is a Stage 2
prerequisite, not solved by this ADR, but flagged so Storage work does
not silently work around it.

---

## Consequences

- Storage (Stage 2) now has a fixed target schema to serialise —
  including two fields (`validator_root`, `consensus_proof`) that do not
  exist in code yet. Storage work should either wait for those fields to
  land, or explicitly version its schema as "v0, pre-consensus-integration"
  and plan a migration.
- `version` field enables forward compatibility: future header changes
  add branches on `version`, not silent breaking changes.
- This ADR does not change `abyss-core` code by itself. Implementation
  is tracked as follow-up work, sequenced before or alongside Stage 2.
