# ADR-0021 — Execution Semantics

**Status:** Accepted
**Date:** July 2026
**Related:** ADR-0019 (State Machine shape), ADR-0020 (Transaction Specification)

---

## Context

ADR-0019 fixed the *shape* of `State` (Accounts, Validators, Treasury,
Contracts, Governance). It deliberately did not define the *rules* that
govern how a transaction changes that state. Per "one ADR = one decision,"
those rules get their own document.

---

## Decision

### Nonce checking (implemented, documented here as final)
A transaction's `nonce` must equal the sender's current nonce exactly.
Enforced today in `Chain::apply_transaction()`. No gap-nonce or replay
tolerance — matches `rejects_replay_nonce` (passing test).

### Fee model (implemented as flat; gas is out of scope for now)
Current: flat `fee: Coin` per transaction, debited alongside `amount`
from the sender (`tx.total_debit()`). **Accepted for the current phase.**
A gas-metered fee model (cost proportional to computation) is explicitly
**out of scope** until Stage 3 execution engine work begins on contract
execution (ADR-0009's EVM-compatible layer) — a flat fee has no
meaningful "computation cost" to meter against for simple transfers.

### Atomicity and rollback (implemented, documented here as final)
A block's transactions execute against a staged copy of `State`. If any
transaction fails, the entire block is rejected and `State` is
unchanged — no partial application. This restates ADR-0004 in execution
terms and is enforced by `Chain::apply_block()`
(`block_application_is_atomic`, passing test).

### Emission (implemented, documented here as final)
Total supply is hard-capped at 55,000,000 AC via `Coin::MAX`
(`coin::tests::supply_is_capped_at_55m_ac`, passing test). There is no
block reward / inflation mechanism in the current model — all AC exists
from genesis (ADR-0015's Genesis Allocation Registry) and is only ever
transferred, never minted post-genesis. If validator rewards require new
emission in the future, that is a **new ADR**, not an amendment to this
one, since it would change a currently-fixed supply guarantee.

### Staking execution (shape defined by ADR-0019; behaviour defined here)
Bonding, unbonding, and jailing operate on `ValidatorState`
(`bonded`, `unbonding`, `jailed` — per ADR-0019):
- `bond(address, amount)`: moves `amount` from `AccountState.balances`
  to `ValidatorState.bonded`. Fails if account balance is insufficient.
- `unbond(address, amount)`: moves `amount` from `bonded` to `unbonding`
  with a `completion_height`; funds remain locked until that height.
- `jail(address)`: called when `abyss-consensus::SlashingRegistry`
  records evidence (ADR-0016 Stage 1). Moves the validator to
  `ValidatorState.jailed`, excluding them from `leader()` rotation and
  from vote-counting toward quorum until unjailed.
- **Slash penalty percentage is explicitly NOT decided by this ADR** —
  it is an economic/governance parameter, not an execution-semantics
  one. Tracked as a separate future decision once Governance
  (ADR-0019's placeholder `GovernanceState`) is designed.
- **Implementation status: not yet written.** This ADR fixes the
  intended behaviour; `bond()`/`unbond()`/`jail()` do not yet exist in
  `abyss-core::state`. Tracked as Stage 2/3 follow-up.

### Shielded operations (explicitly out of scope)
Confidential/shielded transaction execution is Phase 3 territory
(whitepaper Section 5; ADR-0016 Phase 3). This ADR governs only the
current transparent transaction model. A future ADR will define shielded
execution semantics when the privacy layer (ADR-0022) implementation
begins.

### Determinism (implemented, documented here as final)
Execution must be a pure function of `(State, Block)` — no wall-clock
reads, no external randomness, no non-deterministic iteration order
during execution. `State`'s use of `BTreeMap` (not `HashMap`) is a
deliberate consequence of this rule: BTreeMap iteration order is
deterministic; HashMap's is not. Any future addition to `State` must
preserve this property.

---

## Consequences

- Execution behaviour is now documented independently of state shape,
  matching ADR-0020's split of transaction format from block format.
- `bond`/`unbond`/`jail` have a specified contract before they are
  implemented — Stage 2/3 work can build directly against this ADR
  rather than inventing behaviour ad hoc.
- The emission cap is now explicitly flagged as something a future
  validator-reward ADR would need to formally revisit, not silently
  break.
